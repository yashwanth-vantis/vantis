# DECISIONS.md

This file logs every deviation from, or interpretation of, the binding files (`tokens.css`, `usage-rules.md`, `page-spec.md`, `panright-brand-core.md`). If a decision here conflicts with those files, the files win: change the code and remove the entry.

## Hero

**D-01 · Short viewports: resolving the hero open item.**
*Problem.* At 1366×650 the frame is 518px tall at full width. Nav, frame, lead and buttons then need about 720px, so the primary CTA sits below the fold.

*Change.* At 1024px and wider, the hero stage's `max-width` is capped by viewport height:
`max-width: max(40rem, min(100%, (100svh − reserve) × 2.39))`
- `reserve` = nav + top gap + frame-to-lead gap + two lead lines + lead-to-button gap + button + bottom gap.
- The frame, the lead, the buttons and the card all narrow together, so the frame stays exactly 2.39:1.
- On tall screens nothing changes.

The headline gets a matching cap: `font-size: min(--text-display, 14.5cqi − 45px, (cols 1–11 width) / 8.2)`.
- The first term is the token.
- The second keeps three lines inside the frame's inner height.
- The third keeps the widest line of the three-line wrap inside cols 1–11.

A stage narrowed by this rule is centred, like a letterboxed projection, rather than left-aligned with a void beside it. Text inside it stays left-aligned.

*Why this is the smallest change.* It adds one rule on the stage and one `min()` on the headline. It adds no new layout, keeps the copy and the card placement, keeps the frame ratio and keeps one accent per viewport.

*Rejected alternatives:*
- Shrinking gaps (not enough space to gain).
- Moving the CTA into the frame (breaks the spec).
- Letting the frame lose its ratio (breaks the spec).

*Measured* (`reports/hero-fit.txt`; CTA bottom must be ≤ viewport height):

| Viewport | Frame | Ratio | Inner / headline | CTA bottom |
|---|---|---|---|---|
| 1440×900 | 1312 × 549 | 2.39 | 419 / 299.4 | 825 |
| 1440×780 | 1190 × 498 | 2.39 | 368 / 299.4 | 756 |
| 1366×650 | 882 × 369 | 2.39 | 238.8 / 238.5 | 626 |
| 1536×730 | 1071 × 448 | 2.39 | 318 / 299.5 | 706 |
| 1280×720 | 1051 × 440 | 2.39 | 309.8 / 270.5 | 696 |
| 1280×1024 | 1152 × 482 | 2.39 | 352 / 270.5 | 869 |
| 1024×768 | 896 × 375 | 2.39 | 244.9 / 224.0 | 686 |

*Spec comparison.* On tall viewports the fit-check numbers from page-spec.md hold: 1440 → 419 / 299.4 (spec 421.0 / 299.5), 1280 → 352 / 270.5 (spec 354.0 / 270.5), 1024 → 244.9 / 224.0 (spec 246.9 / 224.0). The 2px gap in inner height is the 1px frame border on each side, which the spec arithmetic leaves out.

At 1280×720 and 1440×780 the stage narrows slightly. The two-line lead the spec's totals did not account for would otherwise push the CTA past the fold.

**D-02 · Hero padding on desktop.** Top padding is `nav + --space-4` and bottom padding is `--space-4`. Without the 24px top gap, a narrowed frame's top line touched the nav's bottom border.

**D-03 · Hero content timing.** Content R starts at 50% of the frame pan rather than strictly after it. The headline is the LCP element; starting at 50% keeps mobile LCP under 1.9s. The pan stays visible.

**D-04 · Hero light size.** "60vw × 50vh" is read as the ellipse's diameters: `radial-gradient(30vw 25vh at 20% 50%, …)`. Without JS, or with reduced motion, the light rests at its end position (`translateX(40vw)`).

**D-05 · Hero below 1024px.**
- Tablet (640–1023): the full frame with a `--space-7` inset on all sides.
- Mobile (<640): only the top and bottom lines, as the spec says. The inset applies vertically only, because there are no side lines to inset from; text aligns to the grid margin.
- The glass card stacks below the frame on tablet as well as mobile. The spec only mentions mobile, but the frame grows past 2.39:1 at those widths, so the card cannot straddle its bottom line cleanly.

**D-06 · "PANRIGHT STUDIOS" position.** Read as: on the frame's bottom label row, `--space-3` above the bottom line, with its right edge on col 8. The glass card occupies cols 9–12 at that corner.

## Tokens and type

**D-07 · Font stacks.** tokens.css is copied byte for byte (verified with `cmp`). global.css then redefines `--font-headline`, `--font-body` and `--font-label` to insert metric-matched local fallbacks generated by `scripts/build-fonts.py` (`size-adjust`, `ascent-override`, `descent-override`). Family order is otherwise unchanged. A derived `--font-display` adds an uppercase, expanded-width fallback so the hero does not reflow on swap. Measured CLS is 0.000 on every page.

**D-08 · Self-hosted font files.**
- Fontsource variable builds, latin subset, trimmed with fontTools to the ranges tokens.css uses: Archivo wght 400–600 and wdth 100–125 (42 KB), Hanken Grotesk wght 400–500 (21 KB), IBM Plex Mono 400 and 500 (14 KB each).
- The family is declared as "Archivo", the first name in the token stack.
- Only Archivo and Hanken Grotesk are preloaded. Plex Mono appears only in small labels and swaps without layout shift.

**D-09 · Archivo width verified.** In the browser, "KNOW THE FILM" at `font-stretch: 125%` measures 1.30× its width at 100%: 1019px against 784px at 100px. Width is driven by `font-stretch` alone, with no `font-variation-settings`.

**D-10 · Logo outlining.**
- `logo-a-c.svg` relies on a live `<text>` element. The wordmark was outlined with HarfBuzz and fontTools from the trimmed Archivo, instanced at wdth 125 and wght 500, with kerning on.
- Size 40, tracking 1.6, anchored at the end (x=282) and on the baseline (y=38), matching the source SVG's geometry.
- The frame mark path is unchanged.
- The result is `src/components/Logo.astro`, an inline SVG using `currentColor`.
- page-spec.md lists "Logo outlined in Figma" as a pre-launch item. This outline matches the source, but brand should still sign off on it.

**D-11 · Statement labels in mono.** `THE PREMISE` and `THE BELIEF` use the mono label style. usage-rules.md §5 limits mono to slate data; these are read as scene slugs (section metadata, uppercase, under 40 characters). Switch them to the body font if brand disagrees.

**D-12 · Language.** `lang="en-GB"`, because the brand copy uses British spelling ("optimise").

## Content and placeholders

**D-13 · Placeholders render visibly.**
- `[METHOD FACTS]` is a small muted note under the four method rows. The rows are spec copy pending confirmation.
- Each service row shows its name and `[SERVICE DESCRIPTIONS]`.
- `[CONTACT EMAIL]` is plain text, not a link (there is no address yet).
- `[YEAR]`, `[LEGAL ENTITY]`, `[RESPONSE TIME]` and `[PRIVACY POLICY]` render as written.

**D-14 · New UI microcopy.** These strings are not in the spec. All are functional text only, and none are claims:
- Form: "(optional)" on optional fields, a "Choose one" select option, and field errors: "Required.", "Enter an email address, like name@studio.com." and "Tick to agree before sending."
- Form with no endpoint configured: "Not sent. [FORM ENDPOINT] is not configured yet."
- Mobile menu: the "Close" label.
- "Skip to content".
- 404 page: label `SC 404`, heading "This page is not in the cut.", link "Back to home".
- Privacy and 404 meta titles and descriptions.

**D-15 · Form behaviour.**
- Role, film stage and message are optional; name, production house, work email and consent are required.
- Validation runs on submit. An error clears as soon as the field becomes valid while typing.
- There is no blur validation: a layout change on blur moved the submit button out from under the pointer and swallowed the click (found in testing).
- The spec's error and success messages go to a `role="status"` `aria-live="polite"` region. Fields get `aria-invalid` and `aria-describedby`, and focus moves to the first invalid field.
- With `[FORM ENDPOINT]` unresolved, nothing is sent and nothing is faked.

**D-16 · Error state without red.** usage-rules.md §9 allows eight colours only, so an invalid field gets a 2px `--color-text-primary` border plus a text message. Colour is never the only cue.

**D-17 · Input borders.**
- Inputs use a 1px `--color-text-subtle` border (4.71:1 on raised, 5.42:1 on bg) to meet WCAG 1.4.11 (3:1 for component boundaries). `--border-hair` (1.2:1) would fail.
- On focus the spec says "border to `--color-border-strong`", which is weaker than the resting border. Instead the border goes to `--color-text-muted` and the spec's `--focus-ring` is added.
- The checkbox uses `accent-color: --color-text-primary`, keeping the tungsten accent for the submit button (rule 1).

**D-18 · Headings not shown in the spec.** About has visually hidden h2s ("Working rules", "Company") so the principle cards (h3) and the company note sit under a heading in the outline. Phase and service names include a visually hidden index, so screen readers hear "01 Validate".

**D-19 · Services header.** The spec says "Label and h1 cols 1–9" but gives no label text, so no label is rendered. The anchor row reads `01 VALIDATE / 02 PREPARE / 03 CAPTURE / 04 FINISH` and links to each phase section.

**D-20 · Services section tones.** The header is on bg, then 01 surface, 02 bg, 03 surface, 04 bg, then the CTA band (bg, with its top hairline).

**D-21 · Mobile menu links.** The menu lists Services, About and Contact only, as the spec says. Home is reached through the logo.

## Motion and runtime

**D-22 · Hidden-until-revealed only with JS.**
- An inline head script adds `html.motion-ok` only when `prefers-reduced-motion: no-preference` matches. CSS hides reveal targets only under that class.
- If the GSAP bundle has not started within 3 seconds, the class is removed, so content never stays hidden.
- The class is restored on `astro:after-swap`, because the router replaces the `<html>` attributes.

**D-23 · Reveals use opacity, not visibility.** Keyboard users can always reach content that is mid-reveal. Any element that receives focus while still revealing is finished immediately (`focusin`), so focus never lands on something invisible.

**D-24 · Stagger cap.** Groups stagger at most six items, as the tokens comment says. Items beyond the sixth (none at launch) reveal with the sixth.

**D-25 · Test hook.** `window.__panrightDebug` exposes two read-only counts (active ScrollTriggers and active tweens) so the leak test can verify cleanup. It exposes no state.

**D-26 · Nav positioning.** The nav is `position: sticky` with `margin-bottom: −64px`, so the hero's 64px top padding sits under the glass bar as the spec intends. Other pages pad their first section by nav height plus `--space-9`.

## Build, SEO and deployment

**D-27 · Build gate.**
- `npm run build` runs `check:placeholders` first and fails while any placeholder remains, as required.
- `npm run build:preview` builds without the gate. The delivered `dist/` came from `build:preview`, because placeholders remain by design.

**D-28 · Canonicals use the literal `https://[DOMAIN]`** in canonical tags, Open Graph tags, JSON-LD, sitemap.xml and robots.txt. Astro's `site` option is left unset because it rejects non-URLs.
- Lighthouse SEO scores 83 because the canonical and the robots Sitemap line are not valid URLs. The 404 page scores 50 because it is also, correctly, `noindex`.
- With a test domain substituted in a scratch copy, Home, About and Contact score SEO 100 on mobile and desktop.

**D-29 · Compression.** CloudFront's automatic compression (Brotli and gzip) handles text assets rather than pre-compressed files on S3. Pre-compressed objects would need per-object `Content-Encoding` metadata and break `aws s3 sync`. PNGs are palette-compressed and the fonts are WOFF2.

**D-30 · CSP.** CSS is inlined per page (no render-blocking CSS request), and GSAP writes inline `style` attributes, so the policy uses `style-src 'self' 'unsafe-inline'`. Scripts are hash-locked: the single inline script is allowed by its sha256 (`scripts/csp.mjs` prints the policy). The site was tested under the generated CSP with no console errors.

**D-31 · Playwright.** The asset generator and the tests use the globally installed Playwright through `createRequire`; it is not a dependency in package.json. Locally, run `npx playwright install chromium` once.

## Test hosting

**D-32 · GitHub Pages test deploy.**
- Internal links, icons and the manifest honour Astro's `base`. A build with `BASE_PATH=/vantis/` serves correctly from `https://yashwanth-vantis.github.io/vantis/`. This was verified by serving `dist/` under `/vantis/`: fonts loaded, client navigation and `aria-current` worked, and there were no 404s or console errors.
- The workflow (`.github/workflows/deploy-pages.yml`) uses the ungated preview build and sets `PUBLIC_NOINDEX=true`, so the test site is never indexed with placeholders.
- GitHub Pages cannot set response headers or cache rules, so the CSP, HSTS and immutable caching in `infra/DEPLOY.md` do not apply to the test site.
- Production stays on S3 + CloudFront with `base: "/"`.
